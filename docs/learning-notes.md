# 学习笔记 · RAG Agent 的模块拆解

> 配合本项目代码阅读。目标：把"RAG"从一个模糊概念，拆成 AI Agent 架构里可定位、可替换、可调优的具体模块。

## 一、RAG 在 Agent 架构中的位置

通用 Agent 的五件套是：**感知（Perception）→ 记忆（Memory）→ 规划（Planning）→ 工具（Tools）→ 行动（Action）**。
RAG 本质上不是一个独立应用，而是**给 Agent 装上"外部记忆 + 检索工具"**的组合：

| Agent 模块 | RAG 中的对应物 | 本项目实现 |
| --- | --- | --- |
| 感知 | 文档解析（PDF/DOCX/HTML → 文本） | `src/parsers.js` |
| 记忆（写入） | 分块 + 向量化 + 建索引 | `src/chunk.js`、`src/embed.js`、`src/kb.js` |
| 记忆（读取） | 语义检索 / 关键词检索 / 混合融合 | `src/retrieve.js` |
| 工具 | 检索器、重排器、LLM | `src/retrieve.js`、`src/rerank.js`、`src/llm.js` |
| 规划 | 问题改写、失败后重新规划查询 | `src/rag.js` 的 `rewriteQueries` 与重试循环 |
| 评估 / 反思 | 相似度阈值判定、拒答、补检 | `src/rag.js` 的阈值过滤与 Agent 重试 |
| 行动 | 生成最终答案并给出引用 | `src/rag.js` + 前端溯源展示 |

**关键认知**：很多人把 RAG 理解成"向量库 + 提示词"，但从 Agent 视角看，它是一个**带反馈回路的检索决策系统**——检索不到时能不能换个问法再试，才是 Agent 与普通管道的分水岭。

## 二、记忆模块：分块是决定上限的环节

写入记忆的质量决定了读取的上限。分块的本质矛盾是 **语义完整性 vs 向量区分度**：

- 块越大 → 语义越完整，但向量被稀释（一段里塞了五个主题，跟谁都不太像）
- 块越小 → 向量越精准，但答案缺少上下文（只召回一句话，模型无法作答）

四种策略其实是这个矛盾的不同解法：

| 策略 | 解法思路 | 代价 |
| --- | --- | --- |
| 固定 token | 不管语义，只保证长度可控 | 可能从句子中间切开 |
| 语义切块 | 用相似度找"语义转折处"再切 | 建库需额外调一次向量模型 |
| 段落切块 | 相信作者已经分好段 | 依赖原文排版质量 |
| 递归分隔 | 按结构优先级逐级降级 | 折中方案，无惊喜也无大坑 |

**Overlap（重叠）** 是缓解"边界信息丢失"的补丁。它不改变切块逻辑，只是让相邻块共享一部分内容。经验区间 10%~20%。

## 三、检索模块：为什么必须混合

- **语义检索（稠密向量）**：把文本压缩成一个向量，匹配的是"意思"。强于同义泛化，弱于精确字符串（型号、错误码、条款号）。
- **BM25（稀疏关键词）**：基于词频与逆文档频率，匹配的是"词"。强于精确匹配，弱于语义泛化。二者是**互补而非替代**关系。

融合的两种做法：

- **RRF（倒数排名融合）**：`score = Σ 1/(k + rank)`，只用排名不 care 分数，因此不受量纲影响，鲁棒性最好，是默认推荐。
- **加权求和**：需要先归一化再加权，可解释性强但权重需要调。

**易踩的坑**：如果用"本次结果的最大值"做归一化，第一名永远是 1.0，阈值就彻底失效了。正确做法是除以**理论最大值**（RRF 双路第一 = 2/(k+1)），保证不同查询之间的分数可比——本项目在 `src/retrieve.js` 的 `normalizeCandidates` 里专门处理了这一点。

## 四、重排模块：两阶段检索

一阶段检索（向量）为了速度做近似搜索，召回率高但排序粗糙；二阶段用 **Cross-Encoder** 把 query 和候选片段拼在一起逐对打分，精度显著更高。

代价是速度，所以只在小候选集上做：**召回 20~50 条 → 重排 → 取 Top 3~8 进上下文**。这是工业界的标配结构，也是"检索数量"和"重排数量"必须分开配置的原因。

## 五、规划模块：问题改写

用户的原始提问往往不是最优的检索输入。三类手段：

1. **单查询改写**：补全指代（"它有什么缺点" → "消费贷产品的缺点是什么"），去掉无关修饰。
2. **Multi-Query**：从一个问题生成 N 个不同角度的查询，分别检索后合并去重，提升召回。
3. **HyDE**：先让模型"编"一个假设性答案，用答案去检索——因为答案的表述方式往往更接近原文措辞。

注意改写本身有成本（一次 LLM 调用）和风险（改写跑偏），单轮简单问答可以不改，**多轮对话必须改**。

## 六、评估模块：阈值与拒答

这是产品体验上最容易被忽略、但最能决定"可信度"的一环。

- 没有阈值：模型永远会硬着头皮回答，用通用知识编造一个看起来很像样的答案 → 幻觉。
- 有阈值：低于阈值直接说"依据当前知识库无法回答" → 可信，但可能过度拒答。

调参方法：在检索实验台跑 20~50 个真实问题，记录"相关命中"与"无关命中"的分数分布，取两者分界处。**不要凭感觉设 0.5**。

进阶：把「阈值判定」升级为 Agent 的**反思（Reflection）**步骤——不是直接拒答，而是让模型换个问法再检索一轮（本项目 `agent.maxIterations` 已实现此回路）。

## 七、可观测性：为什么这个项目把每一步都暴露出来

RAG 调参最大的困难是"不知道是哪一步错了"：答案不对，可能是切块切错了、召回没召回、重排排错了，或者模型没按资料答。

所以本项目把改写结果、召回候选与各路分数、重排分数、进入上下文的切片、最终引用全部暴露在界面上。**先能看见，才谈得上调优**——这也是做 RAG 产品和做 RAG demo 的核心区别。

## 八、下一步可以练手的点

1. 建一个评测集（50 条问答 + 标注应命中的切片），把"调参"从主观感受变成可量化指标（召回率、拒答准确率）。
2. 把阈值判定改成模型自评（让 LLM 判断"这些资料够不够回答问题"），对比规则阈值的效果差异。
3. 加入结构化数据召回（表格、产品要素表），观察纯文本切块在结构化信息上的失效场景。
4. 实现真正的迭代式 Agent：检索 → 反思 → 补检 → 再生成，观察 token 成本与准确率的权衡曲线。
